# セルフレビュー

PR 作成前に変更内容をレビューし、問題があれば指摘する。

## 手順

### 1. Issue を確認する

Issue 番号が `$ARGUMENTS` で渡された場合はその Issue を確認する。渡されていない場合はユーザーに確認する。

```bash
gh issue view {番号} --comments
```

Issue の目的・実装内容・非対象・完了条件と、プランのコメントを把握する。

### 2. 変更内容を把握する

```bash
git log main..HEAD --oneline
git diff main...HEAD
```

生成物（`gen/`・`bun.lock`）の diff は読まない。proto の変更を見る。

### 3. 以下の観点でレビューする

#### スコープ

- [ ] Issue の実装内容に含まれる変更のみか
- [ ] Issue の非対象に該当する変更が混入していないか
- [ ] 不要なリファクタリング・コード整理が含まれていないか

#### 品質

- [ ] 既存の設計・パターンを壊していないか
- [ ] proto の変更が後方互換を壊していないか（フィールド番号の再利用・削除、型の変更）
- [ ] 生成物が proto と一致しているか（再生成して差分が出ない）
- [ ] 秘密情報が含まれていないか
- [ ] 不要なライブラリが追加されていないか
- [ ] lint・typecheck・test が通っているか

#### ドキュメント

- [ ] 実装に対応するドキュメント（`docs/`・README）が更新されているか
- [ ] CLAUDE.md の Documentation Rules に従っているか

#### プランとの整合性

- [ ] Issue コメントに投稿されたプランと実装が一致しているか
- [ ] 乖離がある場合、Issue コメントでプランが更新されているか

### 4. 結果を報告する

以下の形式で報告する:

- **OK**: 問題なし。`/pr` で PR を作成して良い
- **要修正**: 問題点を具体的に列挙する。修正後に再度 `/review` を実行する
